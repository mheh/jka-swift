## P1. A view for the ICARUS shared-memory structs

The question. The `sharedMem` local of `vmMain` in `g_main.swift` points at `gSharedBuffer`, and 33 of the 60 Port-notes of `g_main` wait on a view over the `T_G_ICARUS_*` structs. What is the struct in the oracle, does `views.py` make such a view today, and where does the view live?

The proof. Raven declares 17 typedef structs in `g_public.h`, from `T_G_ICARUS_PLAYSOUND` to `T_G_ICARUS_GETSETIDFORSTRING`, and `vmMain` uses all 17. Every field is an `int`, a `float`, a `qboolean`, a `vec3_t`, or a `char[2048]`, and `views.py` already maps each of these shapes, a `char[N]` to a `String` with a `CharBuf` second accessor at lines 340-350 and a `vec3_t` to a `SIMD3` at lines 208 and 273. The C target already includes the 17 headers in `Sources/CJKAMP_Game/include/CJKAMP_Game.h`. The store has no struct schema, so no store fact drives the view set. `views.py` lines 77-79 walk the closure of each root in `ROOTS` of `rulings.py` lines 18-45, a hand list, and `docs/transcription.md` line 82 rules that a struct no root reaches joins `ROOTS`. No root reaches the 17 structs. So the first blocker is the missing `ROOTS` rows, and the view path fits as it stands. The second blocker is the buffer. Raven declares `char gSharedBuffer[8192]` at `g_main.c:881` and hands its address to the engine at `g_main.c:920`, `trap_SV_RegisterSharedMemory(gSharedBuffer)`, so the engine writes the 17 shapes into one fixed address. The skeleton put the Swift `gSharedBuffer` into `GameVariables.swift:419` as a `CharBuf` value, a Swift array with no stable address, and `g_main.swift:1068` holds the register call as a hole. A view binds `raw: UnsafeMutablePointer<T>` at a fixed address, so a view over a `CharBuf` value is not sound. `docs/transcription.md` line 417 rules that a record Raven leaves zero is one zeroed allocation on `GameStorage`, and line 432 gives the same home to a file-scope array the world owns. The buffer is such an array, and the skeleton missed it only because its element is `char`.

The ruling. Replaced. The 17 structs join `ROOTS` in `rulings.py` under `CJKAMP_Game` with the names `IcarusPlaySound`, `IcarusSet`, `IcarusLerp2Pos`, `IcarusLerp2Origin`, `IcarusLerp2Angles`, `IcarusGetTag`, `IcarusLerp2Start`, `IcarusLerp2End`, `IcarusUse`, `IcarusKill`, `IcarusRemove`, `IcarusPlay`, `IcarusGetFloat`, `IcarusGetVector`, `IcarusGetString`, `IcarusSoundIndex`, and `IcarusGetSetIDForString`, and `views.py` writes them on the next generator run. `gSharedBuffer` moves from `GameVariables` to `GameStorage` as one zeroed allocation of `MAX_G_SHARED_BUFFER_SIZE` bytes, born and freed with `GameWorld`, by a name rule in `rulings.py` that `skeleton.py` reads beside the rule of line 417, and the forward in `g_main.swift` gives its base as an `UnsafeMutableRawPointer`. The local `T_G_ICARUS_X *sharedMem = (T_G_ICARUS_X *)gSharedBuffer` is a drafter shape in `draft_declarations.py`: a pointer local cast from a storage byte allocation to a view type is `let sharedMem = IcarusX(handle: OpaquePointer(gSharedBuffer))`, and the register call passes the same base. No hand fix lands in `g_main.swift`.

## P3. The G1 gate and a draft that looks edited

The question. The G1 gate of `draftcheck.py` keeps a function `align.py` marks `edited`, and the re-splice kept `Q_strncpyz` and `Info_NextPair` though no person touched them. How does the gate tell a draft from hand work?

The proof. `align.py` line 83 marks a line `edited` when a replace block of equal length differs from the stored draft line, and line 88 marks the rest `hand`. The stored draft comes from the `lines` table through `store.lowered_lines` at lines 131-135, and the `lines` primary key is `(language, file, function, seq)`, so the store keeps only the newest draft of a function. The G1 gate is `kept` in `draftcheck.py` lines 88-99, and line 95 keeps every function with a `hand`, `edited`, or `rewritten` line. The commit `e1726b6` says a function a person ported stays. For `Q_strncpyz`, the pre-run file at `616965d` lines 729-739 held the older draft byte for byte, the new drafter run added `var destIndex: Int32 = 0` and changed two lines, so the old lines are an equal-length replace block and read `edited`. `Info_NextPair` shows the same pattern with `keyIndex` and `valueIndex`. The store has no splice record, no body hash per function, and no past draft, and `aligned_files.hash` is a whole-file hash, so no store fact today tells a spliced draft from hand work. Only git holds that fact. `notes/2026-10-08/stage-two-steps-8-10-walk.md` lines 139-140 fix the five states and never rule on who wrote an `edited` line, so the gap is unruled.

The ruling. Replaced. The gate records each splice: `draftcheck.py` writes one row per spliced function into a new store table `splices` with the columns `path`, `function`, and `hash`, the hash of the body it wrote, and `kept` reads that table first. A function whose current body hash equals its `splices` row is a draft, and the gate splices over it whatever `align.py` says. A function with no row or another hash stays under the align verdict as today. Bodies spliced before the table exists stay under the align verdict, and the re-splice already moved the two named functions, so no bootstrap pass is needed.

The question. `bodies.py --compile-holes` saves no rows for a function with a compile hole, so align needs a plain run first. Is this by design and documented, or a gap?

The proof. `bodies.py` line 429 reads the rejected statements only under `--compile-holes`, lines 435-437 draft a holed function again in memory and return its rows before any store call, and the only save is `save_lowered` at line 448 on the plain path. The commit `d70b53f` that added the flag says it in its body. `align.py` line 133 reads the `lines` rows, which only the plain run fills, so the plain run before align is the documented order. One correction to the re-splice record: the printer stop on the 11 functions is the stop of `printer.py` lines 162-165, a rejected declaration or scratch or choice statement, not the missing-rows stop of line 155, and the record's wording of the cause is likely wrong while the order it followed is right.

The ruling. Ratified as documented. The in-memory path is by design, three records say so, and no code change lands. A builder who runs align after a compile-holes print runs `bodies.py --stem <stem>` first, as the re-splice did.
