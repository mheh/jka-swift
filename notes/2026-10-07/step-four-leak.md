# The step-four leak diagnosis, 2026-10-07

The builder of stage two holds that the `Drafter` carries state from one function to the next inside a stem, so rows written per function cannot reproduce the stem's text byte for byte. This note reads the drafter for every field that outlives one `draft` call, traces the one path that reads a field before `draft` sets it, runs four probes on temporary stores, and ranks the fixes under the rulings. File and line references name the worktree `.claude/worktrees/agent-ac60452bfe29cede1/tools/oracle-closure/` in its uncommitted state at the time of capture, and the builder may have moved lines since.

## The mechanism

There is one real pre-set read, on one path, in one function, and it risks a crash and changes no printed byte. Every other field the drafter keeps across functions is an artifact.

The real one. `draft` sets the per-function fields in a fixed order, and it runs the pre-scan helper `raw_local_names` at `bodies.py:247` before it sets four fields that the spelling of an expression reads: `table_cursors` from `local_facts` at `bodies.py:252`, `slots_locals` at `bodies.py:258`, `narrow_locals` at `bodies.py:260`, and `optional_vectors` at `bodies.py:272`. `raw_local_names` (`draft_classification.py:398`) asks `is_raw` about every store into a local (`draft_classification.py:425`), `is_raw` asks `raw_store` (`draft_classification.py:134`), and `raw_store` spells the base and the offset through `expr` to build its answer (`draft_classification.py:102`). That spelling path, `expr` (`draft_expressions.py:600`), `cast` (`draft_expressions.py:864`), `base` (`draft_expressions.py:815-816`), `slots_source` (`draft_classification.py:812`), `expr` again (`draft_expressions.py:404-405`), and `reference` (`draft_expressions.py:653-664`), reads `slots_locals`, `narrow_locals`, `table_cursors`, and `optional_vectors`. On a fresh drafter the first of those reads raises `AttributeError`. In stem order each read sees the value the previous function left. The order is the same on wave-0, where the `optional_vectors` line is `bodies.py:237`.

Where it bites. `raw_store` recognizes one shape, Raven's `*(T *)(b + ofs)` or `((T *)(b + ofs))[i]` over a raw pointer, and one function of the 2,513 in the 85 bg and game stems writes such a store into a local: `G_Find` of g_utils, `s = *(char **) ((byte *)from + fieldofs)`. So `bodies.py --only G_Find` crashes today, and a snapshot run with a drafter per function crashes on g_utils, which is the crash the builder saw. In stem order `G_Find` reads the values of `G_TeamCommand`, the function before it. Three of them equal its own, all empty, and `table_cursors` differs, empty against `from` walked by its index, yet the text is the same byte for byte, because `is_raw` keeps only whether `raw_store` gave an answer and discards the spelled text. A stale `optional_vectors` that names every identifier of G_Find's body changes no byte either. The stale read risks the crash and changes no printed byte.

The artifacts, where they are written, where a later function could read them, and the verdict:

- `holes` (`bodies.py:159`). Written at `draft_classification.py:443` and `457` and at `draft_declarations.py:283`. Read only by the footer of `printed` (`bodies.py:383`). Each increment emits exactly one line with the role `note` (`draft_classification.py:449` and `458`, `draft_declarations.py:287`), so the footer is a count of `note` line rows, which `stem_text` computes at `bodies.py:443`.
- `hole_names` (`bodies.py:161`). Written at `draft_classification.py:444` and `draft_declarations.py:284`. Read only at `draftcheck.py:157`, to count a cascade of a hole. `draftcheck.py` builds its own drafter for each pass (`draftcheck.py:126`) and drafts the stem in order (`draftcheck.py:129-130`), so the stored rows never carry this set.
- `compile_holes` and `compile_due` (`bodies.py:192-193`, `draft_statements.py:242`). Gate counters, empty in a `bodies.py` or `snapshot.py` run.
- `statement_keys` and `statement_numbers` (`bodies.py:195-196`, grown at `draft_statements.py:224-227`). The number is the mark `\x00N\x01` that `marked` puts on each line (`draft_classification.py:35-37`), and `draft` strips every mark before it returns (`bodies.py:313`). The key holds the function name (`draft_statements.py:218-220`), so two functions never share a number, and no rule in the five draft modules reads the length of a marked line.
- `logical_tails` (`bodies.py:167`). Written at `draft_expressions.py:538-551` and read at `draft_expressions.py:947-948`, keyed by the stem and the byte span of the operator. The read for a left operand follows the write for that operand inside the draft of the same chain.
- `pending` (`bodies.py:165`). Every statement saves and restores it (`draft_statements.py:207-214`), and so do the else-if arm (`draft_statements.py:843-850`) and the loop head (`draft_statements.py:955-971`). A hoist runs outside a statement frame (`draft_declarations.py:258-270`), so a note it appends at the top level stays in the list and never prints, in the stem draft and the lone draft alike. No function of the 2,513 started with a non-empty `pending`.
- `leaf_wrap`, `scratch_modes`, and `loop_steps` (`bodies.py:172-176`). Each writer sets and restores its field in a `try` and `finally` (`draft_expressions.py:327-332`, `draft_declarations.py:106-110`, `draft_statements.py:977-981`). No function started with any of them open.

- `_sdk_functions` (`draft_calls.py:245-249`). A lazy set from the translation unit, the same for every function of the unit, and the one reason a fresh drafter per game function costs about three seconds.

Outside the drafter, nothing carries. The `Registry` is built once from `Sources/` (`bodies.py:94-146`), and no draft module writes to it. No draft module writes to the `Skeleton` or the `Table`. `Table.locals_of` (`table.py:1316`) computes the facts of a function on the first read and hands the same facts to every later read. `Table.adopted` (`table.py:875`) caches a pure read. `Skeleton.stub` (`skeleton.py:1045`) counts into `self.counts`, which no line reads.

## The evidence

Four probes sit under `/tmp/step4diag/`, each with its output beside it. Every probe sets `table.STORE` to a temporary folder before it builds the skeleton, so the sweep and every lowered row go there, and the builder's `table.sqlite` was never opened.

`probe2.py` drafts each function twice, once with one drafter for the stem and once with a fresh drafter per function, as the builder's script does, and records the drafter's state at the start of each function. bg_pmove, 102 functions: none differs alone, none fails alone, none starts with dirty state. The S30 check on the captured step-4 code lowered 102 of 102 functions in 5 seconds, the text from the rows equals the drafter's text byte for byte, and the warm read equals it and lowers nothing, which is the second S30 test. The per-function drafts equal the stem text without the footer. Six game stems, AnimalNPC with 9 functions, FighterNPC with 23, NPC with 43, NPC_AI_Atst with 9, NPC_AI_Default with 15, and NPC_AI_Droid with 14: all zero. That is 215 functions in 7 stems, and the budget ended there because of the translation-unit walk, which is also why one run of the builder's loop takes about an hour. g_utils was outside the seven, so this probe missed G_Find.

`probe3.py` covers every stem, 2,513 functions in 85 stems, in one pass of 488 seconds with two drafters: today's stem drafter, and a trapped drafter that deletes every field `draft` sets before each function and records any read of a field that is not set yet. One function reads a field before `draft` sets it, G_Find of g_utils, first `optional_vectors` and then `narrow_locals`. Today's stem drafter never crashes. In every other function the text with the fields reset equals the stem-order text.

`probe4.py` drafts G_Find alone, as `--only G_Find` does. It raises `AttributeError: 'Drafter' object has no attribute 'optional_vectors'`, and the traceback is the chain named above, from `draft` at `bodies.py:247` to `reference` at `draft_expressions.py:657`. G_Find is function 13 of 66 in g_utils, after G_TeamCommand.

`probe5.py` drafts G_Find with a drafter that serves each missing field from G_Find's own values at the first read. It completes and prints today's text byte for byte, and the fields in the order of the first read are `optional_vectors`, `narrow_locals`, `slots_locals`, and `table_cursors`. The stale values from G_TeamCommand are an empty set, an empty dict, an empty set, and an empty dict, and G_Find's own are the same except `table_cursors`, which holds `from` over `g_entities` by `fromIndex`. A second drafter computes each of the four fields by its own helper at the first read, in that order, and it completes with the same text and meets no cycle, so the reorder of `draft` is feasible. A third drafter serves a stale `optional_vectors` that names every identifier of G_Find's body, and the text does not change.

## The affected functions

G_Find of g_utils, one of 2,513. It fails alone and prints the same text in stem order. No other function reads a field before `draft` sets it, and no function drafts differently alone. The builder's loop, run to its end, prints one line after about an hour: `g_utils G_Find: fails alone, AttributeError: 'Drafter' object has no attribute 'optional_vectors'`. The captured step-4 code lowers per stem, so it passes S30 on bg_pmove and would pass on g_utils, but a per-function lowering without the fix below crashes when G_Find is the first function a run drafts.

## The fix options, ranked

The drafter fix comes first, as its own commit before step 4.

1. Reorder `draft`. Move the four assignments above the `raw_locals` line at `bodies.py:247`: the `optional_vectors` comprehension at `bodies.py:272-273`, the `local_facts` line at `bodies.py:252` with its comments, `slots_locals` at `bodies.py:258`, and `narrow_locals` at `bodies.py:260`. The gate is the tool tests, `bodies.py --only G_Find` with no error, and `snapshot.py --check` against the step-1 snapshot, which drafts every function, so a helper that reads one more unset field in another function stops there and names it. The reorder is proven on G_Find, the one function that takes the path. Recommended.
2. Split recognition from spelling in `raw_store`, so `is_raw` never runs `expr` inside a pre-scan. This removes the dependence of the pre-scan on the spelling state for good, and it is a rule change with a wider blast radius, so it belongs to stage three.
3. Give the four fields empty values in `__init__`. This removes the crash, but the pre-scan then reads empties instead of the function's own values, which is a hidden wrong read. Not recommended.

The stage-two options, with the drafter fix in place:

1. Keep S14 as ruled. The lowering runs per function on the first read, and `Lowering` holds one drafter for the run, so a function lowers in any order and a `--only` run pays for its functions alone. After the reorder no state crosses a function, so there is nothing to carry. This is the recommendation.
2. Define per function as per function in stem order with the stem's state, which is the shape of the captured diff. It passes the gate, but it departs from S14 without a mechanism behind it once the drafter is fixed, it costs a `--only` run the draft of the whole stem, and without the fix it still crashes a run whose first function is G_Find.
3. Carry the state in rows. Nothing qualifies. The counter is a query under S38, the marks are stripped before any row exists, the four pre-set fields are the function's own facts and the fix computes them in place, and the cascade set belongs to `draftcheck.py`.
4. Carry the state in the key. The key names inputs, and no input differs between a lone draft and a stem draft.
5. Amend a ruling. None is needed. One finding for step 5 under S38: the footer must count `note` line rows, not `lowered` rows, because S9 gives a `DECL_STMT` with two failed declarations one `hole` row while the drafter counts two holes and writes two `note` lines. The captured `stem_text` counts `note` lines at `bodies.py:443`, which matches the drafter, and the printer of step 5 should keep that query.
